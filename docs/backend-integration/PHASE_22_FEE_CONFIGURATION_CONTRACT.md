# Phase 22 — Fee Configuration Contract

This document records the Django 5.1.6 / DRF 3.15.2 source contract audited for Phase 22. It does not contain credentials or production financial data. Django source and `postman_collection.json` are authoritative; the legacy React Native mock model is not.

1. **Fee Head endpoints.** `GET, POST /fee-heads/`; `GET, PATCH, DELETE /fee-heads/{id}/`; and `PATCH /fee-heads/{id}/status/` exist.
2. **Fee Structure endpoints.** No standalone Fee Structure list, detail, create, update, delete, activation, or status endpoint exists. `FeeStructure` is an internal one-to-one parent of `SchoolClass` and is created by the first Item POST.
3. **Structure Item endpoints.** `GET, POST /fee-structure-items/` and `GET, PATCH, DELETE /fee-structure-items/{id}/` exist. Items are separate resources, not a nested Structure payload.
4. **Discount/concession endpoints.** No configuration-level discount, concession-definition, or Student-concession endpoint was found. Phase 22 marks these unsupported.
5. **Fine-rule endpoints.** No configuration-level fine-rule endpoint was found. Generated-invoice fine fields are not configuration resources and remain out of scope.
6. **Methods and paths.** The app uses only the relative authenticated paths above. Phase 22 exposes Head list/detail/create/update/status and Item list/detail/create/update. It deliberately omits both confirmed DELETE methods.
7. **Authentication.** Every fee view uses DRF authentication. A missing/expired token produces the shared `401` refresh/session-expiry flow; `403` is retained as a permission error.
8. **Role permissions.** Fee Head reads require an authenticated user with a School; mutations require backend role `admin`. Item reads are branch-scoped for `admin`, `branch_admin`, or `teacher`; mutations require `admin` or `branch_admin`. The Phase 22 navigation is narrower: School Admin and Branch Admin only; Teacher has no fee-configuration workspace.
9. **Request DTOs.** Head create/update: `{name, frequency}`. Head status: `{is_active: boolean}`. Item create: `{school_class, fee_head, amount, is_mandatory}`. Item PATCH: changed `amount` and/or `is_mandatory` only.
10. **Response DTOs.** Heads contain `id, school, name, frequency, is_active, created_at`. Items contain `id, school_class, fee_head, amount, is_mandatory, created_at`.
11. **Response envelopes.** Lists use `{success:true, fee_heads:[...]}` or `{success:true, fee_structure_items:[...]}`. Detail/mutation responses use singular `fee_head` or `fee_structure_item`. Mappers reject a missing key, non-true success flag, invalid field type, or unknown enum.
12. **Success status codes.** List/detail/PATCH return `200`; create returns `201`; confirmed DELETE returns `200` with a success message rather than `204`.
13. **Amount unit and precision.** `FeeStructureItem.amount` is Django `DecimalField(max_digits=10, decimal_places=2)`: decimal rupees with a maximum of `99999999.99`. DRF transports it as a fixed-scale string. Internal authoritative arithmetic uses non-negative integer paise.
14. **Currency behaviour.** Django has no currency field on the fee resources. The product displays INR by existing app convention only after exact paise mapping. Request DTOs are canonical, unformatted decimal strings and never locale strings.
15. **Writable/read-only fields.** Head `name` and `frequency` are writable; School, ID, active status on create/update, and timestamp are server-controlled. Item create accepts Class, Head, amount, mandatory; update accepts only amount and mandatory. Parent Structure and timestamp are server-controlled.
16. **Ownership.** Fee Heads are School-wide. A Structure belongs to exactly one Class, and therefore inherits that Class's Branch, Academic Session, and School. An Item belongs to that Structure and references one same-School Fee Head.
17. **Structure/Item relationship.** `FeeStructure.school_class` is one-to-one. `FeeStructureItem.structure` is many-to-one. The frontend models a Class fee blueprint keyed by the real Class ID and never invents an exposed Structure ID.
18. **Frequency values.** Fee Head accepts exactly `monthly` or `one_time`, mapped to `MONTHLY` and `ONE_TIME`. Items do not carry a separate frequency; they inherit Head semantics.
19. **Date/schedule behaviour.** Fee configuration has no effective date, due date, academic-month list, instalment count, quarterly/half-yearly schedule, or custom schedule field. Monthly due generation and explicit one-time generation are later server operations.
20. **Lifecycle values.** Fee Head has only boolean active/inactive. Fee Structure and Item have no draft, active, inactive, archived, or locked status.
21. **Activation and side effects.** No Structure activation operation exists. Creating or editing a Head/Item does not itself generate invoices or Student liabilities. A later invoice-generation endpoint reads current configuration.
22. **Editing an “active” Structure.** There is no active Structure state. Item amount and mandatory flag remain patchable. Existing invoice items store snapshot amounts, so subsequent configuration edits do not rewrite those invoice snapshots.
23. **Copy behaviour.** No server copy endpoint or transactional copy service exists. The frontend disables copying and does not clone records client-side.
24. **Discount semantics.** No confirmed definition exists. Mock percentage/fixed discounts and Student assignments remain isolated demo data and are not mapped to live Students.
25. **Fine semantics.** No confirmed configuration rule exists. Mock fixed/daily/slab rules are not authoritative and are unavailable from the live workspace.
26. **Uniqueness.** Fee Head is unique by `(school, name)`. Fee Structure is unique by one-to-one Class. Structure Item is unique by `(structure, fee_head)`. Backend duplicate errors use `DUPLICATE_FEE_HEAD` or `DUPLICATE_FEE_STRUCTURE_ITEM` with `400`.
27. **Query parameters.** Item list supports optional `school_class`. Fee Head list exposes no confirmed query parameter. Search in Phase 22 is documented client-side filtering over the complete returned list.
28. **Pagination.** Neither confirmed list is paginated. The frontend exposes real array counts and does not fabricate pages or pagination metadata.
29. **Filtering and ordering.** Backend views provide no confirmed search/status filter or explicit ordering. Class scoping is achieved with the exact `school_class` Item filter. UI name filtering and display ordering are local and documented.
30. **Deletion/cascade/protection.** Head DELETE is blocked with `HAS_DEPENDENTS` if Structure Items, Student assignments, or invoice items reference it. Item DELETE hard-deletes configuration; existing invoice snapshots survive. Class/Structure deletion cascades to Items at model level. Phase 22 exposes no deletion because dependency policy is not sufficiently safe for casual mobile use.
31. **Validation errors.** Serializer errors and named duplicate/dependency errors return `400`. Frontend maps `school_class→classId`, `fee_head→feeHeadId`, `is_mandatory→mandatory`, and preserves non-field messages. It additionally rejects malformed/negative/excess-precision/non-canonical money.
32. **Permission errors.** Backend mutation denial is `403`; missing School can be `404 NO_SCHOOL`; inaccessible object lookup is `404`. The frontend does not turn `403` into logout and does not retry uncertain mutations automatically.
33. **School Admin.** Can read and mutate School-wide Heads, and read/create/update Items for Classes in accessible School Branches. The client uses live School/Branch/Session/Class identities and sends no School ID in fee payloads.
34. **Branch Admin.** Can read School-wide Heads but cannot mutate them. Can read/create/update Items only for the assigned Branch. A missing or mismatched Branch does not broaden access.
35. **Super Admin.** Backend fee views depend on `request.user.school`; Super Admin is platform-only in the app and receives no current-School fee routes.
36. **Inactive-context enforcement.** Backend Item views validate branch accessibility and same-School relationships, but do not enforce active School, Branch, Session, Class, or Head parents. The frontend selects only active Branches/Classes/Heads for new Items, blocks closed-Session and inactive-Class mutations, and labels these honestly as frontend safeguards.
37. **Frontend/backend mapping.** Django DTO → defensive mapper → live Head/Item service → explicit integration resolver → current fee configuration store → screen. Conceptual Structure totals use checked integer-paise addition across confirmed Item amounts.
38. **Unsupported frontend operations.** Rich names/codes/descriptions, effective dates, draft/activation, preview, copying, bulk/nested saves, deletion, schedules, discounts, fines, Student assignments, overrides, exemptions, and payable previews are unavailable in live configuration.
39. **Django/Postman/frontend mismatches.** Postman describes Head and Item endpoints and decimal strings but no standalone Structure resource. The prior mock UI assumed a Branch/Session/Class Structure aggregate with statuses, schedules, fines, discounts, copies, and Student assignment counts; none are transported to Django.
40. **Risks before Due generation.** Configuration updates are independent requests, not an atomic multi-item aggregate; the Item update serializer lacks the create serializer's explicit non-negative minimum, so the frontend enforces non-negative values; inactive-parent rules remain frontend-only; there is no version/optimistic concurrency field; and Phase 23 must audit invoice-generation idempotency, frequency selection, Student assignment semantics, snapshots, and authorization before connecting any live liability workflow.

## Isolation decision

The legacy `feeSetupService` and its demo identities remain available only through `fee-setup-demo` for later mock workflows. Phase 22 screens use the new live services. Live Class, Head, Item, or Student IDs are never passed into mock due-generation repositories.
